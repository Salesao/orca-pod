# Изменения orca-pod и отдельный pi-task

Дата: 11 ноября 2026 года.

Статус: дизайн явно утверждён пользователем 11 ноября 2026 года.
Ранее запрошенный приоритет асинхронного окна уже реализован. Последующее
требование запускать Codex Planner в Plan mode и использовать там обычное окно
выбора пока внесено в дизайн. Остальной процесс и выделение pi-task ещё не реализованы.

Это русская версия требований для чтения и утверждения. Подробности устройства,
источники и критерии проверки также записаны в
[английском документе](2026-11-11-orca-pod-workflow-design.md).
Два документа описывают одни решения; при расхождении перевод исправляется до
реализации, а новый продуктовый выбор не делается без пользователя.

## Зачем нужны изменения

По результатам запусков нужно сократить лишние проверки, сохранить решения
пользователя при составлении плана, исправить случайное делегирование при
выключенных помощниках и упростить их специализации. Qoder и OMP должны стать
полноценными вариантами для ролей. Окно вопросов Pi выделяется в отдельный
репозиторий pi-task, который владелец позднее опубликует в Pi Packages.

В локальных отчётах есть массовые неудачные запуски помощников из-за исключённых
расширений провайдера, последовательный обход вместо параллельной работы,
проблемы памяти, повторная проверка сотен файлов и устаревшие сообщения о
неисправностях. Отдельно зафиксирована лишняя самопроверка исполнителя при
наличии проверяющих. Эти случаи определяют изменения; отчёты не позволяют
обещать конкретный процент ускорения.

## Уже принятые решения

1. Блиц проводится по спецификации и дизайну, затем по плану.
2. Ответы по-прежнему выбирает пользователь. Planner предлагает варианты на
   основе согласованных документов и показывает расхождения.
3. Во время работы Pi Lens применяется точечно. В конце обычный Reviewer
   проверяет все изменения задачи; после исправлений — исправленные файлы.
   Проверка затронутых потребителей общих интерфейсов ниже предложена как уточнение автора.
4. Вне Pi используются доступные проверки выбранной программы и проверки из
   плана; обязательного Pi Lens через MCP нет.
5. В каждой роли не больше трёх специализаций помощников. Число одновременно
   работающих экземпляров остаётся отдельной настройкой.
6. В конфигурации не больше трёх профилей.
7. Выключенное делегирование должно отражаться в запуске роли, её инструкциях и
   доступных инструментах, насколько это позволяет программа.
8. Добавляются Qoder и OMP.
9. pi-task получает отдельный репозиторий. Публикацию выполняет пользователь.
10. Пользователь выбирает варианты в окне, как в pi-task. По последнему уточнению
    в Codex Plan mode первым используется request_user_input. Вне Plan сохраняется
    ранее выбранный асинхронный вариант, если он доступен и разрешён. Текст —
    только при недоступности подходящих окон или по просьбе пользователя.
11. Если через orca-cli открывается роль Planner с Codex, до передачи задания
    включается настоящий Plan mode. Режим запуска остальных ролей не меняется.

## Ответы первого блица

| Вопрос | Выбранное поведение |
| --- | --- |
| 1. Запрет помощников нельзя полностью обеспечить | Продолжить с предупреждением и явным запретом в задании |
| 2. Обязательная проверка недоступна | Завершить с заметной пометкой о неполной проверке |
| 3. Исправления после замечаний Chief | Их проверяет только Chief, без возвращения к обычному Reviewer |
| 4. Лимит повторных проверок | Общие три попытки для последнего этапа и его полной диагностики |
| 5. Ответ по плану меняет прежнее решение | Показать изменения в обоих документах и подтвердить их вместе |
| 6. В старых настройках больше трёх профилей | Автоматически оставить активный и два первых остальных; сохранить полную резервную копию |
| 7. Собственные специализации | Разрешить заменять ими готовые места, сохраняя предел в три |
| 8. Помощник не работает без тяжёлой проверки | Основная роль выполняет эту работу сама |

## Рассмотренные варианты

Для диагностики рассматривались обязательная проверка каждого этапа и точечные
вызовы. Выбраны точечные вызовы с одним общим проходом в конце.

Для разных программ рассматривались собственные средства проверки и единый
Pi Lens через дополнительный сервер. Выбраны собственные средства: меньше
обязательных зависимостей, но набор диагностик может различаться.

Для окна вопросов рассматривались самостоятельный пакет внутри orca-pod и
отдельный репозиторий. Выбран отдельный репозиторий с независимой установкой.

Предлагаемое устройство сохраняет нынешние терминалы Orca и навыки. Общие
описания возможностей программ связывают форму настройки, проверку конфигурации
и запуск. Новый постоянно работающий управляющий сервис не добавляется.

## Планирование и вопросы

Если спецификация и дизайн существуют отдельно, блиц покрывает оба документа.
Если они объединены, достаточно одного блица по общему документу. Отдельный
визуальный дизайн не создаётся искусственно для задачи, которой он не нужен.

Принятые решения получают короткие устойчивые обозначения в документах:
решение, источник, раздел и отметку о том, принято ли оно пользователем или
предложено автором. Отдельная база истории не нужна.

Planner сопоставляет каждый существенный выбор плана с предыдущими решениями:
совпадение, противоречие, новый выбор либо подробность реализации без изменения
согласованного результата. Совпадения достаточно показать в обзоре. Противоречия
и новые решения с настоящими альтернативами становятся вопросами. Простую ошибку
переноса исправляют до блица, без лишнего вопроса.

Пользователь выбирает ответы сам. Если ответ меняет спецификацию или дизайн,
Planner обновляет исходный документ и план, показывает изменения и получает
одно общее утверждение новых версий. Противоречие между двумя утверждёнными
документами не разрешается выдуманным приоритетом.

Карточки остаются понятными без чтения исходника. Отмена, пустой ответ,
предвыбранный вариант и истечение времени не означают согласия. Сохраняются
нынешние ограничения раундов, обзор, путь к документу и явное утверждение.

В Codex Plan mode первым используется request_user_input с отдельно выбираемыми
вариантами и описаниями. Вне Plan первым остаётся разрешённое асинхронное окно:
карточка и вопрос идут в заголовке; польза и цена каждого варианта — в его тексте.
Агент сохраняет ход активным и ждёт настоящего ответа. Если основной инструмент
недоступен, используется оставшееся разрешённое окно. Режим Default сам по себе
не доказывает недоступность всех окон. Правила среды о допустимости инструментов
и утверждений сохраняются.

В Pi используется pi-task. Другие программы используют свои окна вопросов;
при их подтверждённой недоступности остаётся пронумерованный текст.

### Запуск Codex Planner в Plan mode

До первого задания, в том числе при подготовке пустого терминала, Planner должен
уже находиться в настоящем Plan mode. Инструкция «ты планировщик», режим файлов
только для чтения и прежний флаг доступности вопросов не заменяют переключения.
Глобальные настройки Codex для этого не меняются.

В установленном Codex 0.166.0 нет флага запуска --plan. Поддерживается
[интерактивная команда /plan](https://learn.chatgpt.com/docs/developer-commands?surface=cli#switch-to-plan-mode-with-plan).
Предложенная последовательность:

1. Открыть Codex с настройками роли, пока без задания.
2. Через orca-cli дождаться готовности интерфейса; запрос доверия к папке должен
   быть разрешён до следующей отправки.
3. Отправить /plan и Enter в записанный терминал Planner.
4. Проверить действительный режим по экрану или поддерживаемому состоянию
   сессии. Только затем один раз отправить задание. Принятие ввода само по себе
   не доказывает переключения; при неудаче сообщить о проблеме запуска.

Изменяется подготовка роли, а не только текст задания модели. При реализации
нужно проверить распознавание режима и настоящее окно выбора в терминале Orca.
Такой полный запуск пока не проверялся. В текущем чате попытка обычного окна
вернула ошибку его недоступности в Default mode. Нынешний навык с безусловным
приоритетом асинхронного окна потребуется обновить под новое правило режима.

### Сохранение дизайна и плана

Установленный Codex запрещает в Plan mode записывать файлы, в том числе документы
планирования. Промпт роли и передача записи помощнику не обходят этот запрет.

Предложение автора: исследование, обсуждение и блиц проходят в Plan. Для записи
предусматривается отдельная узкая фаза вне Plan в той же сессии Planner — только
для названных документов и журнала решений. Затем режим Plan возвращается и
проверяется до следующих вопросов или утверждения. Черновик сохраняется до
блица по документу; изменения по ответам — до утверждения окончательной версии.
Запись документов не разрешает реализацию плана или изменение приложения.

Конкретное управление выходом и возвратом нужно проверить при реализации.
Нельзя предполагать, что повторный /plan выключает режим или что это сделает
обычная просьба модели. Если среда не позволяет выполнить эту фазу, ограничение
показывается явно. Дополнительная специализация помощника, постоянный цикл
Coordinator или отдельный сервис для записи не добавляются.

## Роли и помощники

Предложенный набор специализаций:

| Основная роль | Специализации |
| --- | --- |
| Planner | Scout, Researcher, Oracle |
| Implementer | Worker, Scout, Verifier только при отсутствии проверяющих |
| Reviewer | Reviewer, Scout |
| Chief Reviewer | Reviewer, Evidence Auditor, Scout |

Scout исполнителя также получает ограниченное исследование внешних источников,
если программа предоставляет нужные инструменты. Отдельный lens-checker
удаляется: диагностика принадлежит основной роли.

Явно выбранный набор помощников заменяет набор по умолчанию, а не прибавляется
к нему. Собственные специализации занимают те же три места. Встроенные
помощники программы не используются как незаявленная четвёртая специализация.
Несколько работников одной специализации остаются допустимыми в пределах
отдельной настройки параллельности. Рекурсивное делегирование запрещено.

При выключенном делегировании роль выполняет работу сама. Ей не регистрируют
помощников проекта и, где возможно, отключают инструменты делегирования.
Безусловные указания вызвать разведчиков, работников и проверяющих заменяются
условными. Политика повторяется в коротких передачах заданий и закрепляется в
долговременных инструкциях роли.

Если установленная программа не обеспечивает полное отключение, она остаётся
доступной с явным предупреждением. Инструкция не выдаётся за техническую
гарантию. Это защита от случайного делегирования, а не изоляция всех возможных
действий через командную строку.

При наличии внешних проверяющих Implementer не запускает собственные аудиты,
даже если обычные помощники ему разрешены.

## Диагностика и возврат исправлений

В плане указываются ответственный, охват заключительной проверки, доступное
средство, точные разрешённые проверки, запасной вариант и обязательность.
Проверяющим разрешаются указанные в плане проверки без изменения исходников.
Это не разрешение автоматически исправлять, форматировать, собирать программу
или запускать тесты. Правило о тестах только по запросу пользователя сохраняется.

Исполнитель передаёт накопленный список изменений всей задачи, включая новые
и переименованные файлы, удаления и затронутые связи. Предшествующие посторонние
изменения и служебные отчёты не приписываются задаче. Без Git используется
явный перечень изменений.

Полный проход выполняется при первой проверке последнего этапа. Он охватывает
и изменения предыдущих этапов. Для каждой относящейся к задаче части указывается,
проверена ли она, не поддерживается ли средством проверки или проверка к ней
неприменима. Нет сообщений — ещё не доказательство выполненного анализа.

После подтверждённых ошибок исполнитель возвращает исправления тому, кто
запросил их. Повторная диагностика охватывает исправленные части и затронутых
потребителей. Средство, умеющее проверять только весь проект, работает в своём
минимальном допустимом объёме; это ограничение отмечается в отчёте.

Обычный Reviewer выполняет первоначальную полную проверку. Chief не повторяет
её автоматически. Если Chief требует дальнейшие исправления, он сам проверяет
их своими доступными средствами; возврата к обычному Reviewer нет.

Если обычного Reviewer нет, первоначальная диагностика принадлежит Chief.
Если нет обоих, её выполняет Implementer; Verifier может проверять критерии и
запланированные команды, но не поднимает отдельный Pi Lens. В таком режиме
результат не выдаётся за независимое ревью.

Пределы не обнуляются из-за новых диагностик. Для последнего этапа вместе с
полным проходом остаются три попытки. Для Chief сохраняются два захода при
наличии отдельного Reviewer и три финальных захода у единственного проверяющего.
Самопроверка сохраняет предел в три попытки. Подтверждённые серьёзные дефекты
после исчерпания соответствующего предела приводят к остановке по прежним правилам.

## Недоступная проверка и устаревшие сообщения

В отчёте сохраняются ответственный, фактическое средство, охват, неподдержанные
части, ограничения свежести, длительность при наличии и результат проверки.
Устаревшее сообщение сверяется с текущими исходниками и свежей проверкой;
оно не становится заданием на изменение кода автоматически.

У вызовов есть конечное время ожидания. Разрешена не более чем одна точечная
повторная попытка, затем предусмотренная замена. Практические сроки выбирает
разработчик с учётом средства проверки и фиксирует их в реализации.

Если обязательная проверка всё равно недоступна, остальные полезные проверки
продолжаются. Когда иных незавершённых обязанностей и подтверждённых блокирующих
дефектов нет, работа заканчивается статусом COMPLETED_UNVERIFIED: в отчёте и
сообщении пользователю заметно перечислены непроверенные части и причины.
Дополнительного разрешения на такой исход не требуется. Этот исход не называется
FINAL_APPROVED или SELF_VERIFIED и не означает, что отсутствующая проверка прошла.

Подтверждённые серьёзные дефекты по-прежнему требуют исправления и могут привести
к BLOCKED. Недоступность средства не отменяет уже найденную ошибку.

## Расширения Pi

Помощники сохраняют расширения, необходимые выбранному провайдеру модели.
Тяжёлые средства диагностики у работников и проверяющих помощников по умолчанию
не загружаются. Настройки владельца не переписываются глобально; имя его
конкретного расширения не становится универсальным требованием проекта.

Нужно проверить фактическую загрузку и поведение расширений: одной просьбы
модели не вызывать проверку недостаточно, если расширение запускает её само.
Основной ответственный сохраняет Pi Lens; остальные роли используют доступный
точечный режим без обязательных полных проходов.

Если установленная версия не позволяет отделить нужный провайдер от тяжёлой
проверки, основная роль выполняет работу сама. Массовые попытки запустить
заведомо несовместимых помощников не выполняются.

## Три профиля и переход со старых настроек

Предел проверяется при сохранении, обработке формы и запуске. Четвёртый профиль
в неизменённой конфигурации не запускается.

Во время обновления настроек или подготовки запуска старый набор больше трёх
автоматически сокращается: активный профиль и два первых остальных в исходном
порядке. Перед заменой сохраняется полная резервная копия под свободным именем.
Показываются оставленные и убранные профили и место копии. Их внутренние
настройки и активный выбор сохраняются.

Если активный профиль отсутствует, исходник изменился за время операции или
резервную копию сохранить нельзя, исходник не перезаписывается. Сообщается
конкретная проблема. Обычный проверяющий конфигурацию код остаётся читающим;
подготовка запуска отдельно выполняет исправление и повторяет проверку.

Это отдельная операция обновления, завершённая до открытия формы. Её результат
показывается пользователю; отмена последующей формы не вносит новых изменений.
Копия не удаляется автоматически. Инструкция восстановления объясняет, как
вернуть любые три профиля из полного прежнего набора.

Несовместимые настройки специализаций показываются без потери данных. Удаление
старого lens-checker и объединение исследователя исполнителя со Scout проходят
через настройку. Если у объединяемых помощников разные модели или глубина

## Qoder и OMP

Поддержка включает обнаружение программы, форму настройки, доступные модели и
глубину рассуждений, проверку конфигурации, запуск каждой роли, помощников,
политику делегирования, вопросы пользователю и документацию.

Существующая частичная поддержка OMP используется как начало. Оба новых
варианта проверяются по установленной версии и официальным возможностям;
неподдерживаемые параметры не передаются наугад.

Получение списка моделей не должно отправлять запрос к ИИ или показывать
учётные данные. Если список недоступен, возможен ручной ввод с явным указанием,
что выбор не удалось проверить по списку. Неизвестные возможности рассуждений
не заменяются выдуманными уровнями; используется штатный вариант программы.

Роли остаются интерактивными терминалами Orca. Для настройки используется
существующая браузерная форма. Помощники работают через механизм своей
программы, без дополнительных терминалов основных ролей или рабочих копий.
Расширенные права остаются явной настройкой и не снимают запрет делегирования.

## Самостоятельный pi-task

Предложенное место отдельного локального репозитория:
`/Users/salesao/Desktop/worksApp/pi-task`. Создание удалённого репозитория,
отправка изменений и публикация в эту работу не входят. Если имя пакета уже
занято, имя репозитория сохраняется, а имя публикации согласуется до публикации.

Выделяется существующее окно вопросов orca_pod_ask и его независимая логика:
вопросы, варианты, пояснения, свободный ввод, вкладки, отправка, отмена,
завершение при прерывании и сообщения об отсутствии интерфейса. Начальные
ограничения сохраняются: до четырёх вопросов и от двух до четырёх вариантов.

Предложенное имя инструмента — pi_task. Это окно вопросов, а не запускатель
помощников. Расширение возвращает ответы и однозначный результат взаимодействия;
смысл ответа и правила утверждения принадлежат вызывающему навыку.

Пакет устанавливается без orca-pod. Сохраняются лицензия и сведения об исходном
компоненте. Логика блица и форма настройки остаются в orca-pod.

В переходный период plan-blitz предпочитает новый инструмент, затем уже
установленный старый и только затем текст. Новый пакет сам не регистрирует
старое имя, чтобы избежать двойной регистрации. Новое расширение настройки
предоставляет только форму настройки, без копии окна вопросов.

До публикации документируется установка из локального репозитория. Настройка
показывает инструкцию при отсутствии пакета, но не предполагает, что ещё не
опубликованный пакет можно скачать. Разработка проверяет совместную работу
двух проектов в отдельном окружении.

## Границы и проверка результата

Сохраняются нынешние режимы ревью, необязательность Git, версии утверждённых
документов, неизменяемые отчёты, категории замечаний и ограниченные повторы.
Новый сервис, восстановление прерванных запусков и общий предел в три
одновременных помощника не добавляются. Прикладные проекты из отчётов не меняются.
Их частные данные и исходные изменения не публикуются вместе с этим проектом.

Существующие локальные изменения владельца сохраняются. Во время запуска задачи
не устанавливаются недостающие программы и не переписываются глобальные
расширения или учётные данные.

Проверка реализации должна подтвердить пределы профилей и специализаций,
сохранность копии при автоматическом сокращении, условные указания делегирования,
один накопительный проход и ограниченные повторы, корректный исход неполной
проверки, работу новых программ и самостоятельную установку pi-task.
Для Codex Planner отдельно проверяются вход в Plan до задания, выбор через
обычное окно, сохранение документов и возврат в Plan. Неудачное переключение
не должно приводить к отправке задания; остальные роли сохраняют прежний запуск.
Нужны проверки отсутствия повторной отправки, потери ответов, изменений приложения
и утверждения версии, которая ещё не сохранена.

Используются существующие проверки проекта и содержательные проверки поведения.
Для команд программ применяются изолированные настройки; отдельно отмечается,
что проверено реальным запуском, а что — только на небольшом образце. Проверки
не должны просто повторять формулировки инструкций.

Производительность оценивается прежде всего числом вызовов и охватом файлов.
Время зависит от окружения. Полные прогоны приложений из отчётов не нужны:
достаточно небольших примеров нескольких этапов, исправления одного файла,
изменения общего интерфейса, устаревших сообщений и отключённых помощников.
