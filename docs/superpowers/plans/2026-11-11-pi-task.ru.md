# pi-task Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Выделить существующее окно вопросов Pi в самостоятельный локальный репозиторий pi-task, сохранив выбор вариантов, свободный ответ и корректную отмену.

**Architecture:** Независимая логика окна получает компоненты Pi через параметры. Тонкий адаптер регистрирует только pi_task и управляет жизненным циклом; смысл ответов и утверждений остаётся у вызывающего навыка. Установка через манифест пакета не зависит от соседнего orca-pod.

**Tech Stack:** JavaScript ESM, Pi extension API / pi-tui, node:test, npm package manifest, Git.

**Spec:** [Утверждённый дизайн](../specs/2026-11-11-orca-pod-workflow-design.ru.md), [подробная версия](../specs/2026-11-11-orca-pod-workflow-design.md), commit `25a9d75`.

## Global Constraints

- Репозиторий и отображаемое имя пакета — `pi-task`; инструмент — `pi_task`.
- Создать только локальный Git-репозиторий. Не создавать remote, не отправлять изменения и не публиковать пакет.
- Сохранить MIT-лицензию и атрибуцию исходного questionnaire Pi и кода orca-pod.
- Пределы: 1–4 вопроса, 2–4 варианта, заголовок до 12 символов, контекст до 600 символов.
- Сохранить описания, вкладки, свободный ответ, Submit, Esc, обработку прерывания и отсутствия интерфейса.
- Не добавлять автоматический выбор/отправку, историю вопросов, запуск задач или правила утверждения плана.
- Исходники и основные инструкции — английские; русский текст документации — в `*.ru.md`.
- Не менять установленные пользователем расширения или настройки Pi при разработке; проверки установки изолированы.
- Node >=18 для независимой логики и тестов; требования к Node у самого Pi определяет установленный совместимый хост.

## Review Focus

1. Прерывание во время редактирования ответа не возвращает частичное согласие — P1/P2.
2. Два вопроса с одинаковыми заголовками не теряют ответы: порядок сохраняется массивом — P1.
3. Перенос строк, узкий экран и изменение ширины не скрывают варианты — P1.
4. Загрузка без orca-pod и без соседних каталогов действительно работает — P3.
5. Одновременная установка старого расширения настройки не создаёт два инструмента с одним именем — P2/P3.

## Файлы и интерфейсы

Все создаваемые пути ниже относятся к новому репозиторию.

| Файл | Ответственность |
| --- | --- |
| `src/ask.js` | Нормализация входа, компонент окна и читаемый результат |
| `src/result.js` | Единый структурированный исход взаимодействия |
| `extensions/index.js` | Загрузка API Pi, регистрация pi_task, остановка открытых окон |
| `test/ask.test.mjs` | Проверки поведения компонента с подставным набором Pi UI |
| `test/extension.test.mjs` | Регистрация, выходные данные, отсутствие UI, cleanup |
| `test/package.test.mjs` | Независимость упаковки и состав архива |
| `package.json`, `LICENSE`, `NOTICE`, `.gitignore` | Установка, лицензия и состав репозитория |
| `README.md`, `README.ru.md` | Использование, локальная установка, совместимость и будущая публикация |

Переносимые источники из orca-pod: `skills/orca-pod-setup/pi-extension/ask.js`,
блок регистрации `orca_pod_ask` и загрузчик Pi из `pi-extension/index.js`,
поведенческие проверки `scripts/ask-tool.test.mjs` и относящиеся к вопросам
проверки `scripts/pi-extension.test.mjs`. Исходные файлы здесь не удаляются:
удаление выполняет O9 после проверки самостоятельного пакета.

`Question = {question, header, context?, options: [{label, description?}]}`.
`Answer = {header, kind: 'option'|'text', label}`; массив сохраняет порядок вопросов.
`TaskResult = {status: 'submitted'|'cancelled'|'aborted'|'no-ui'|'invalid', answers: Answer[], reason?, mode?, error?}`.
Пустой либо прерванный результат никогда не превращается в `submitted`.
Каждый исход возвращается в `details` и `structuredContent`, а `content` содержит
один текстовый блок с читаемым результатом. Объекты details/structuredContent
описывают один и тот же исход; имя варианта не становится ключом объекта.

## Волны и этапы

Последовательно P1 → P2 → P3. После каждого шага с изменением поведения —
указанные проверки; после P3 — самостоятельный пакет, готовый для O9.
Commit делается только по перечисленным файлам после проверки. Публикации нет.

### P1. Перенести независимое окно без изменения взаимодействия

**dependsOn:** нет. **writeScope:** `src/ask.js`, `test/ask.test.mjs`, `package.json`, `LICENSE`, `NOTICE`, `.gitignore`.

**Interfaces:** сохраняются `ASK_LIMITS`, `normalizeAskParams(params)`,
`createAskComponent({questions,tui,theme,kit,signal,done})`, `askResultText(result)`.
Результат нормализации: `{ok:true, questions}` либо `{ok:false,error}`.
Компонент вызывает `done` ровно один раз; работа с клавишами остаётся прежней.

- [ ] Проверить отсутствие занятого каталога; создать отдельный Git-репозиторий и минимальный ESM-манифест с `name: "pi-task"`, `version: "0.1.0"`, `license: "MIT"`, `test: "node --test test/*.test.mjs"`.
- [ ] Перенести исходник окна и существующие поведенческие проверки, сохранив происхождение кода в NOTICE; удалить упоминания plan-blitz из результата отмены, оставив только факт отсутствия ответа.
- [ ] Добавить проверки: одинаковые заголовки дают два ответа по порядку; Esc/abort после первого ответа дают пустой массив; повторный abort/Enter после завершения не вызывает done второй раз; изменение ширины пересчитывает отображение.
- [ ] Проверить точные границы 1/4/5 вопросов, 2/4/5 вариантов, 12/13 символов заголовка, 600/601 символ контекста и повторяющиеся названия вариантов.
- [ ] Выполнить `node --test test/ask.test.mjs`; все проверки проходят, тесты не загружают Pi и не требуют доступа к модели.
- [ ] Зафиксировать перечисленные файлы: `feat: extract reusable Pi question UI`.

### P2. Зарегистрировать самостоятельный инструмент и единые исходы

**dependsOn:** P1. **writeScope:** `extensions/index.js`, `src/result.js`, `src/ask.js`, `test/extension.test.mjs`, `test/ask.test.mjs`, `package.json`.

**Interfaces:** `normalizeTaskResult(raw) -> TaskResult` в `src/result.js`;
`default async function register(pi)` в `extensions/index.js` регистрирует
`pi_task` с входом `{questions: Question[]}`. Извлечённый `askResultText` принимает
новый status и при необходимости прежние внутренние reason/cancelled для
перехода; наружу выдаётся только TaskResult.

- [ ] Добавить проверки регистрации ровно одного `pi_task`, отсутствия `orca_pod_ask`/`orca_pod_setup` и совпадения текстового и структурированного исходов.
- [ ] Добавить проверки `submitted`, Esc, уже прерванного signal, abort во время окна, `session_shutdown`, invalid до открытия UI и no-ui для print/json/rpc.
- [ ] Реализовать нормализацию: успешный исход требует ответов; отмена/abort/no-ui/invalid возвращают `answers: []`; незавершённый `ui.custom` не является успехом.
- [ ] Перенести только нужные Pi-загрузчик, схему вопросов, UI-вызов и cleanup; поддержать оба существующих пространства имён пакетов Pi через текущий механизм динамического импорта.
- [ ] Указать `pi.extensions: ["./extensions/index.js"]` в package.json; разрешить упаковку extensions/src/LICENSE/NOTICE/README*. Никаких импортов orca-pod, формы настройки, браузерного сервера или аккаунтов.
- [ ] Выполнить `node --test test/ask.test.mjs test/extension.test.mjs`; проверить, что listeners и активные контроллеры удаляются во всех исходах.
- [ ] Зафиксировать изменения: `feat: expose standalone pi_task extension`.

### P3. Проверить установку и подготовить документацию пакета

**dependsOn:** P2. **writeScope:** `README.md`, `README.ru.md`, `test/package.test.mjs`, `package.json`, `NOTICE`; временные артефакты вне рабочего дерева.

**Interfaces:** результат — устанавливаемый локально пакет, версия 0.1.0,
инструмент pi_task из P2. O9 использует установленный инструмент; зависимости
на относительный путь соседнего репозитория в коде orca-pod не появляется.

- [ ] Добавить package-тест, который проверяет `npm pack --dry-run --json`: entrypoint и src входят в архив; настройки, секреты, node_modules и файлы orca-pod отсутствуют.
- [ ] Описать вход и все пять исходов; различить название пакета и инструмента. Показать выбор варианта и свободный ответ, сохранив нынешнее поведение одного вопроса и Submit для нескольких.
- [ ] Проверить команду локальной установки по документации установленного Pi и записать её в обе README; будущую registry-установку обозначить как доступную после публикации владельцем, не как уже работающую.
- [ ] Выполнить `npm test` и `npm pack --dry-run --json`; ожидаются успешные проверки и правильный состав архива.
- [ ] В изолированной конфигурации Pi установить локальный пакет без orca-pod, открыть окно и проверить выбор, свободный ответ и отмену. Путь к изолированной конфигурации задавать поддерживаемым механизмом Pi; не менять системные HOME/CODEX_HOME или пользовательские расширения.
