## Global Constraints

- Конфигурация: 1–3 профиля; до 3 выбранных специализаций на основную роль.
- Параллельность остаётся `max_subagents`: default 6, диапазон 1–100. Число запусков отдельно не ограничивается.
- Режимы `full`, `reviewer`, `chief`, `self`, необязательность Git и неизменяемые утверждённые версии документов сохраняются.
- Каталоги: Planner scout/researcher/oracle; Implementer worker/scout/verifier только в self; Reviewer reviewer/scout; Chief reviewer/evidence-auditor/scout.
- Явный набор помощников заменяет стандартный. Собственные специализации занимают те же три места; рекурсивное делегирование запрещено.
- `use_subagents:false`: работа основной роли, отсутствие регистрации помощников и запрет обхода через другие CLI. Неполное техническое отключение обозначается предупреждением, а не скрытым разрешением.
- В Pi дети сохраняют расширения провайдера моделей и не запускают тяжёлые диагностические расширения; при невозможности разделить их работа выполняется основной ролью.
- Полная диагностика один раз по накопленным изменениям в конце. Повторы — исправленные файлы и затронутые потребители интерфейса; Chief проверяет собственные поздние исправления.
- Три попытки последнего этапа включают диагностику; при отдельном Reviewer у Chief две попытки, у единственного проверяющего три; self сохраняет предел три.
- На таймаут/устаревший результат — один точечный повтор, затем разрешённый запасной способ. Недоступность обязательной проверки без блокирующих дефектов ведёт к `COMPLETED_UNVERIFIED`.
- Проверки без изменения исходников не разрешают автоисправление, форматирование, сборку или тесты приложения. Продуктовое правило «тесты только по запросу» сохраняется. Проверки самого этого изменения перечислены ниже согласно утверждённому дизайну.
- Автоматически оставлять активный профиль и два первых остальных только после полной резервной копии. Настройки помощников с конфликтами переносить через форму без потери выбора модели.
- Codex Planner входит в настоящий Plan до задания и использует обычное окно выбора. Запись документов — отдельная разрешённая фаза вне Plan, не запись через субагента.
- Не устанавливать глобально провайдеры, не менять учётные данные и расширения владельца, не публиковать pi-task.
- Сохранить существующие пользовательские изменения `.gitignore` и пяти Pi-файлов с `subagentOnlyExtensions`; не включать их автоматически в коммиты.
- Сохранить уже начатые изменения plan-blitz/README/тестов; O9 уточняет их, а не откатывает к HEAD.
- Исходники английские, тексты интерфейса в i18n, документация EN/RU. Новые проверки должны проверять поведение, а не только наличие строк в инструкциях.

Утверждённое дополнение пользователя: Coordinator запрашивает поддерживаемый
YOLO при запуске каждой роли. `full_access` управляет прямым запуском.
Делегирование независимо от прав; уровень enforcement и фактические права
попадают в результат разрешения роли. Покрытие: O1, O4, O5, O8 и O10.

## Review Focus

1. Активный профиль стоит четвёртым, исходный файл меняется во время обновления или backup не записывается: исходник не теряется — O3.
2. Явно выбрана одна собственная специализация, но launcher прибавляет стандартные: запускается только выбранная — O2/O5.
3. Утрачена готовность терминала или принят только текст /plan: первое задание не теряется и не отправляется дважды — O8.
4. Исправление общего интерфейса ломает неизменённого потребителя, а Lens возвращает устаревшие данные: проверить затронутого потребителя и свежесть — O7.
5. Провайдер установлен, но каталог/управление reasoning недоступны: настройки не выдумываются, остаётся явный ввод модели и честный предел возможностей — O4/O5.

## Контракты между задачами

- `RolePolicy = {role, provider, reviewMode, useSubagents, helpers, maxSubagents, language, diagnosticOwner}`; `helpers` — массив `{name,model,thinking}`, пустой при отключении.
- `resolveRolePolicy(resolvedProfile, role) -> RolePolicy` в role-policy.mjs. Профиль берётся из существующего resolveProfile, policy ничего не запускает и не пишет.
- `ProviderCapabilities = {provider, version, source, reasoning, delegation, questions, diagnostics, plannerMode}`. `reasoning` содержит `kind: 'levels'|'provider-default'|'unknown'` и подтверждённые уровни; `delegation` различает native/tool-filtered/instruction-only и способ выбора помощников. Остальные разделы описывают проверенный интерфейс, либо явное отсутствие.
- `getProviderCapabilities(provider, evidence) -> ProviderCapabilities` в provider-capabilities.mjs; evidence получается из read-only обнаружения O1/O4. Отсутствие evidence не означает поддержку.
- `providerCommand(settings, options) -> string[]` сохраняет нынешний результат argv; options дополнены `policy` и `capabilities`. Побочных эффектов нет. launcher отвечает за проверку и запуск.
- `ProfileReduction = {changed, sourceHash, nextText, kept, archived}`; `planProfileReduction(source) -> ProfileReduction`, `upgradeProfiles(file, {fsOps?}) -> {status:'unchanged'|'upgraded', backupPath?, kept, archived}`. Ошибка бросается до подмены исходника.
- `DiagnosticEvidence` живёт в существующем отчёте: owner, tool/version, scope, checked, unsupported, freshness, duration, outcome и причина неполноты. Нового постоянного хранилища нет.

`thinking: "default"` — выбранное представление управления со стороны провайдера
для Qoder/OMP, когда это подтверждено их возможностями. Оно приводит к отсутствию
флага reasoning. Для Pi/Codex/Claude сохраняются существующие явные допустимые
значения. Неизвестные уровни не превращаются в придуманный список.

## Волны, зависимости и ревью

По умолчанию последовательное исполнение; возможность независимой работы не
является разрешением запускать помощников. Каждая задача завершается своими
проверками и отдельным коммитом только её файлов. Общий независимый обзор — O10.

| Этап | Задачи | Зависимости |
| --- | --- | --- |
| A | O1, затем P1–P3 отдельного плана | Дизайн утверждён; самостоятельные результаты |
| B | O2 → O3 → O4 → O5 | Общая политика раньше формы и команд |
| C | O6 → O7 → O8 | O5; O8 также требует успешного доказательства O1 |
| D | O9 → O10 | P3 и O7/O8; совместная проверка и ревью |

Если O1 выявит невозможность записи документов с возвратом в Plan, O8 нельзя
считать выполненной или незаметно заменить другим поведением. Продолжить
независимые задачи, затем отдельно решить обнаруженное ограничение с пользователем.

## Заключительная диагностика этого изменения

Владелец — общий проверяющий O10; исполнитель передаёт накопленный список
своих изменений из обоих репозиториев и исходные посторонние изменения отдельно.
Если выбранный способ исполнения не предоставляет независимого проверяющего,
это изменение плана нужно явно согласовать, не выдавая самопроверку за ревью.

| Файлы | Разрешённая проверка | Обязательность |
| --- | --- | --- |
| Изменённые `.mjs`/`.js` | `node --check <file>` для каждого файла | Обязательная проверка синтаксиса, не типов или runtime API |
| Изменённые `.sh` | `bash -n <file>` | Обязательная проверка синтаксиса |
| Markdown, TOML, HTML/CSS, манифесты | Проверка содержания и связей; LSP только при подтверждённой поддержке | Синтаксическая диагностика N/A там, где нет подходящего средства; ручное ревью обязательно |

В Pi можно дополнить проверку `lens_diagnostics` с явным списком и проверкой
свежести. В текущем Codex Lens не предполагается установленным; MCP не требуется.
На команду проверки синтаксиса — 10 секунд и максимум один повтор; запасной
способ — доступный анализатор с явно подтверждённым покрытием той же проверки.
Если такого способа нет, обязательная проверка остаётся неполной. `npm test`
из задач исполняет реализация; это не дополнительное разрешение проверяющему
запускать тесты или менять исходники. После замечаний повторяются диагностика
исправленных файлов и проверка затронутых зависимостей; исходный полный набор
автоматически не сканируется снова. Сохраняются доказательства охвата и свежести.
